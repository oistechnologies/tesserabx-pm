# Changelog

All notable changes to `tesserabx-pm` are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Pre-1.0 development happens directly on `main`. Phases are tracked here as `[Unreleased]` sections until v1.0.0 is tagged, at which point post-v1 work moves to feature branches per the BUILD-PLAN §4.3.

## [Unreleased]

### Phase 12b: AI Completions (Summarize, Suggest, Explain) + Priority Scoring Widget

- `PriorityScoringService@tesserabx-pm` (new `models/services/PriorityScoringService.bx`) ships a deterministic 0-100 priority scorer for PM tasks. Weighting per BUILD-PLAN §12 (urgent=40 / high=25 / medium=10 / low=5, +40 overdue / +25 due within 24h / +10 due within 7d, +10 age bonus for tasks open longer than 14 days, capped at 100). `scoreBreakdown( task )` returns the same numbers plus a `reasons[]` array used both by the widget tooltip and the AI Explain prompt; `topForAgent( agentId )` walks every open assigned task and returns the highest-scored one. The service is AI-free and the widget renders the score at all times.
- `SummarizationService@tesserabx-pm` (new) calls `AiMiddleware.complete( feature : "tesserabx-pm.summarize-thread" )` to summarize a PM comment thread. The prompt asks the model to respond with JSON shaped as `{ summary, keyPoints[], nextStep }`; the service parses via `AiMiddleware.extractJsonObject` (tolerant of code fences / preamble) and falls back to the raw text as the summary if JSON parsing fails. Returns an outcome-tagged struct (`ok` / `disabled` / `error`); short-circuits to `disabled` when `AiCapability.isEnabled()` is false.
- `SuggestionService@tesserabx-pm` (new) ships `suggestAssignees(...)` and `suggestLabels(...)` for a candidate task. v1 strategy is semantic similarity over the embedding index from Phase 12a, scoped to the same project: pulls the top-10 similar historical tasks via `SimilarityService.findSimilarToText`, then aggregates the (assignee_type, assignee_id) and label_id columns across those tasks ranked by count + max similarity. No LLM call in the suggestion ranking itself; the `tesserabx-pm.suggest-assignee` AI feature stays registered so a future v1.1 LLM ranker is a drop-in swap.
- `PriorityExplain@tesserabx-pm` (new wire + flat template) is the AI Explain affordance on the "My recommended next task" widget. Single mount param (`taskId`); the wire builds a prompt from `PriorityScoringService.scoreBreakdown` and calls `AiMiddleware.complete( feature : "tesserabx-pm.explain-priority" )`, rendering the one-sentence rationale inline. The widget partial conditionally embeds this wire via `getInstance( dsl : "AiCapability@ai" ).isEnabled()` so the Explain button is absent when AI is off.
- `views/widgets/recommended_next_task.bxm` (new partial) is the dashboard widget body. The host's dashboard renderer hands the `PriorityScoringService.topForAgent` result through as `data = { task, score, breakdown }`. Renders task title (linked), score badge, priority + due-date chips, the `reasons[]` array as a bullet list, and (when AI is on) the PriorityExplain wire embed. Empty-state copy when the agent has no open assigned tasks.
- `CommentThread@tesserabx-pm` (Phase 4a wire) gains a `summarizeThread()` action + `clearSummary()` action + a `aiEnabled()` template helper. New "Summarize" button at the top of the thread (visible only when AI is on AND the thread has comments) routes through `SummarizationService.summarizeThread`; the result panel renders the summary paragraph, key-points list, next-step suggestion, and a close button. Failure modes (AI disabled, AI error, exception) render an in-place warning rather than crashing the thread.
- Manifest deltas:
  - `aiFeatures` extended with `tesserabx-pm.summarize-thread`, `tesserabx-pm.suggest-assignee`, `tesserabx-pm.explain-priority` (all `kind : "completion"`); the Phase 12a `tesserabx-pm.task-embed` embedding feature stays.
  - `dashboardWidgets` extended with `pm.recommendedNextTask` (data provider `PriorityScoringService@tesserabx-pm.topForAgent`, default grid `col-12 col-md-6`, sort weight 700, gated on `pm.view`, zone `agent-home`).
  - Three new WireBox bindings (PriorityScoringService, SummarizationService, SuggestionService); CommentThread + PriorityExplain wires resolve through ColdBox's per-module auto-resolve.
- `InstallSpec` adds 5 new probes: bindings for the three new services, a probe for the three Phase 12b AI features, and a probe for the `pm.recommendedNextTask` widget registration. 84 specs total in InstallSpec; full suite: 939 specs green.
- Deferred to Phase 13 polish: an inline "Suggest assignee / labels" affordance on the task new / edit forms (the `SuggestionService` is wired and ready; needs a small wire on the task form). The host's account-search API for the assignee picker also lands in Phase 13.

### Phase 12a: AI Embeddings + Semantic Similarity

- `pm_tasks.embedding` column added via migration `2026_05_25_000010_add_embedding_to_pm_tasks.cfc` (`vector(1536)`) plus an HNSW index using `vector_cosine_ops`. Dimension is fixed to match the host's default OpenAI `text-embedding-3-small` model and the host's `kb_articles.embedding` column; changing `AI_EMBEDDING_MODEL` to a model of a different dimension requires altering the column too. pgvector is enabled application-wide by the host's baseline extensions migration.
- `TaskEmbeddingConsumer@tesserabx-pm` (new `models/ai/TaskEmbeddingConsumer.bx`) implements the `EmbeddingConsumerRegistry@ai` contract: `getTextForEmbedding(taskId)` returns the task's trimmed title joined to its trimmed description (separated by a blank line, both signals available without title overweight); `saveEmbedding(taskId, vector)` persists the vector via `cast( :v as vector )` so the JDBC named-parameter parser does not collide with the `::vector` shorthand (same trick `KbIndexingService` uses); `listEntitiesNeedingIndex(limit)` returns un-deleted task ids whose embedding column is still NULL.
- `SimilarityService@tesserabx-pm` (new `models/services/SimilarityService.bx`) ships two entry points. `findSimilarToTask(taskId, limit, excludeSelf=true)` pulls the source task's stored embedding text literal and runs cosine nearest-neighbor (`<=>`) against `pm_tasks.embedding` so the Related Tasks panel does not re-embed on every render. `findSimilarToText(text, limit, projectId)` embeds the supplied free text on the fly via `AiMiddleware.embed` and queries; used by future find-similar-on-create suggestions. Both short-circuit to an empty array when AI is disabled OR the source has no embedding yet. Distance returned is cosine (0=identical, 2=opposite); the UI converts to a similarity percentage for display.
- `PmTaskEmbedder` interceptor (new `interceptors/PmTaskEmbedder.bx`) listens to `onPmTaskCreated` and immediately fetches the task's embedding via `AiMiddleware.embed` then hands the vector to the consumer's `saveEmbedding`. Lazily resolves `AiMiddleware@ai` and `TaskEmbeddingConsumer@tesserabx-pm` via `wirebox.getInstance` because module interceptors instantiate before per-module bindings (same pattern Phase 4b's `ProjectEventLogger` uses). Short-circuits silently when AI is disabled or the text is empty; the host's hourly `ai:embedding-sweep` task is the catch-all for tasks whose embedding drifts from the current text on subsequent updates.
- `RelatedTasks@tesserabx-pm` (new wire + template) embedded on the agent task show page's right column. Renders the top-5 nearest neighbors with similarity percentage badges (computed from cosine distance via `numberFormat( ( 1 - ( clamped / 2 ) ) * 100, "0" )`). Template wrapped in `<bx:if arrayLen( local.matches )>` so the panel hides entirely when empty (matches the Phase 11 linked-tasks-panel empty-state convention). AI-off invariant: the service short-circuits to `[]` when AI is disabled, so the panel naturally collapses without any extra `requiresAi` gating in the template.
- `admin.EmbeddingBackfill@tesserabx-pm` (new handler at `handlers/admin/EmbeddingBackfill.bx`) wraps the host's `EmbeddingScheduler@ai.runOnce` and exposes it as a one-shot operator action at `POST /agent/admin/pm/embed-backlog`. Lets an admin backfill PM task embeddings on demand without waiting for the hourly sweep (useful after a bulk import or right after Phase 12a lands). Returns the per-consumer report as JSON; accepts an optional `limit` body param (default 200) so a large backlog can drain in one request. The first attempt at this path was a CommandBox task script (`tasks/EmbedBacklog.bx`), but CommandBox task runners execute outside the ColdBox app's WireBox container, so the wiring did not resolve; the handler design is correct and reuses the host's well-tested scheduler code path. Backfill from a logged-in admin browser console: `fetch('/agent/admin/pm/embed-backlog', { method : 'POST' }).then( r => r.json() ).then( console.log )`.
- Manifest deltas: `contributesTo` extended with `aiFeatures` + `embeddingConsumers`; `aiFeatures` declares one entry (`tesserabx-pm.task-embed`, `kind : "embedding"`); `embeddingConsumers` declares one entry (`tesserabx-pm.task`, pointing at the `TaskEmbeddingConsumer@tesserabx-pm` mapping with dimension 1536); the `interceptors` array adds the `PmTaskEmbedder` registration. Per the AI-isolation rule (CLAUDE.md §2), no PM code imports `bx-ai` directly; every AI call routes through `AiMiddleware@ai`.
- `InstallSpec` adds 4 new probes: `SimilarityService` binding, `TaskEmbeddingConsumer` binding, the `tesserabx-pm.task-embed` AI feature in `AiFeatureRegistry@ai`, and the `tesserabx-pm.task` embedding consumer in `EmbeddingConsumerRegistry@ai` (including assertions that the consumer's `mapping`, `feature`, and `dimension` come through correctly). 79 specs total in InstallSpec. Full suite: 933 specs green.
- Deferred to Phase 12b: completion features (summarize on `CommentThread`, suggest-assignee / suggest-label, deterministic priority scoring + AI explain), the "My recommended next task" dashboard widget, and a find-similar-on-create UI for new task titles (the `SimilarityService.findSimilarToText` entry point is in place and ready to wire in).

### Phase 9b: Scheduled Due-Soon and Overdue Notifications

- `PmTaskDueScanService@tesserabx-pm` ships two pure-SQL scanners. `scanDueSoon( hoursAhead = 24 )` walks `pm_tasks` for un-completed un-deleted assigned tasks whose due date falls within the window and announces `onPmTaskDueSoon` for each. `scanOverdue()` does the same for past-due un-completed tasks (assigned or not — the dispatcher gracefully skips when assignee metadata is missing). Both fire sync canonical envelopes through `EventPayloadBuilder@core`; `PmNotificationDispatcher` translates each into a `NotificationsService.dispatchForEvent` call targeting the assignee.
- New `pm_task_notify_state` table dedupes scanner output across runs: one row per task, `due_soon_at` / `overdue_at` timestamps mark when the scanner last fired each event. The scanner skips tasks with the matching column already set so the every-15-minute cadence does not re-notify on every run. `resetState( taskId )` (plus an operator `DELETE FROM pm_task_notify_state WHERE task_id = '...'`) re-arms a notification if the task's due date moves.
- Schema note: the migration uses a synthetic `id` primary key plus a UNIQUE on `task_id` because qb's `.primaryKey()` on a non-`id` column generates a constraint that still references `id`. The application layer treats `task_id` as the row identity through an `INSERT ... ON CONFLICT ( task_id ) DO UPDATE` upsert in the service.
- New PM module `config/Scheduler.bx` extending `coldbox.system.web.tasks.ColdBoxScheduler`. Two tasks register every 15 minutes:
  - `pm:scan-due-soon` → `PmTaskDueScanService.scanDueSoon()`
  - `pm:scan-overdue`  → `PmTaskDueScanService.scanOverdue()`
  Both gate on `SCHEDULER_MODE=true` (matches the host's pattern in `config/Scheduler.bx`) so app + worker containers do not double-fire. Closure bodies use the block-statement form per the host's note about BoxLang's closure scope walker recursing on the single-expression form.
- `PmNotificationDispatcher` gains listeners for `onPmTaskDueSoon` and `onPmTaskOverdue`; both target the task's assignee with the standard task context (taskTitle, projectName, dueDate, taskId).
- Manifest deltas: `customInterceptionPoints` adds the two scanner events, `webhookEvents` adds `tesserabx-pm.task_due_soon` + `tesserabx-pm.task_overdue`, `notificationTemplates` adds 8 entries (inapp + email × agent + contact for each of the two new events).
- New test bundle `PmTaskDueScanServiceSpec` (6 specs covering both scanners' positive + dedup + skip paths plus `resetState`). `InstallSpec` adds 3 new probes: PmTaskDueScanService binding, the two new webhook keys, and a per-tuple probe for the 8 new notification templates. 63 specs total in InstallSpec.

### Phase 9a: Notification Dispatch and Templates

- `PmNotificationDispatcher` interceptor translates PM lifecycle envelopes into `NotificationsService.dispatchForEvent` calls. Listeners:
  - `onPmTaskAssigned` → the assignee (skipping self-assignment so the agent who assigns themselves does not self-notify).
  - `onPmCommentAdded` → every watcher of the commentable minus the comment author. Comment events on a task surface the task's title in the template context; project / subtask commentables fall back to ids.
  - `onPmMentioned` → the mentioned user (one notification per `(comment, mentioned user)` tuple).
  - `onPmTaskCompleted` and `onPmTaskStatusChanged` → every watcher of the task minus the actor who triggered the change.
- `MentionService.recordMentions` now announces `onPmMentioned` per parsed mention (sync, best-effort) so the dispatcher can fan out to the mentioned user. Envelope carries `metadata.mentioned_type`, `mentioned_id`, `commentable_type`, `commentable_id`, and `comment_id` for downstream listeners.
- `notificationTemplates` manifest declares 15 entries covering every `(event, channel, recipientType)` tuple Phase 9a owns: `task_assigned`, `comment_added`, and `mentioned` each get inapp + email × agent + contact (4 entries each = 12); `task_completed` gets inapp + email × agent (2 entries); `task_status_changed` gets inapp × agent only to keep email noise down (1 entry). All templates use the host's `{{key}}` substitution syntax (the renderer is a simple key-replace loop; no conditional helpers) so a sparse context renders cleanly without leaving template syntax in the body. Admins override via the `notification_templates` DB table at runtime.
- New webhook event key `tesserabx-pm.mentioned` declared in `webhookEvents` so external webhook subscribers can react to PM mentions; matches the new `onPmMentioned` interception point already declared in Phase 4b.
- Actor name resolution: the dispatcher resolves `actorLabel` from `agents` / `contacts` (full name when present, email when not, type+truncated id when the lookup fails) so the templates read like prose rather than UUID badges.
- `contributesTo` extended with `notificationTemplates`. Manifest interceptor list adds `PmNotificationDispatcher`.
- `InstallSpec` adds 2 new probes: the `tesserabx-pm.mentioned` webhook event registration and a per-tuple probe asserting every Phase 9a notification template lands in `NotificationTemplateRegistry@notifications`. 57 specs total in InstallSpec.
- Deferred to Phase 9b: scheduled tasks for `onPmTaskDueSoon` and `onPmTaskOverdue` plus matching templates. The dispatcher already follows the watcher-fan-out pattern those events will use, so the deferred work is the scheduler config + the event announces + the two new template tuples.

### Phase 8a: Bidirectional Ticket Integration (Linking + Panels)

- `TaskTicketService@tesserabx-pm` ships the link / unlink / list surface over `pm_task_tickets`. `link(data)` is idempotent via `INSERT ... ON CONFLICT (task_id, ticket_id) DO NOTHING`; `unlink(taskId, ticketId)` is a delete; `setLinkType(taskId, ticketId, linkType)` mutates an existing row. `link_type` is constrained to `related | blocks | fixes`. ### Phase 6b: Per-Project Custom Fields

- `CustomFieldService@tesserabx-pm` ships per-project custom field definitions plus polymorphic value storage over Task / Subtask. Seven field types per BUILD-PLAN §6: `text`, `number`, `date`, `dropdown`, `multiselect`, `checkbox`, `url`. `field_type` is intentionally immutable after create (changing it would silently invalidate stored values; delete-and-recreate is the migration path); name, applies_to, required flag, sort order, and options are mutable.
- Per-type `validateAndSerialize(field, rawValue)` enforces the BUILD-PLAN validation matrix:
  - `text` — passes through as-is.
  - `number` — `isNumeric` guard, stored as a decimal string.
  - `date` — `isDate` guard, normalised to ISO `yyyy-mm-dd`.
  - `checkbox` — coerced to `"true"`/`"false"`.
  - `url` — must start with `http://` or `https://`.
  - `dropdown` — value must be in the field's `options_json` set.
  - `multiselect` — every chosen value must be in `options_json`; stored as a JSON-encoded array of distinct values.
  - Required check fires across every type: an empty value on a required field throws `CustomFieldService.RequiredField`.
- Value storage uses `INSERT ... ON CONFLICT (custom_field_id, valuable_type, valuable_id) DO UPDATE` so `setValue` is idempotent and never produces duplicate rows; `setValue` with an empty value on an optional field clears the row instead. `valuesForValuable(valuableType, valuableId)` returns a decoded map keyed by `custom_field_id` (multiselect → array, checkbox → boolean, everything else → string).
