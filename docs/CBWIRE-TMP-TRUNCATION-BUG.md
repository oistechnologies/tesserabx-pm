# CBWire Wire-Template tmp-File Truncation Bug

**Status:** unresolved, sidestepped with a workaround. Filed here so we can reproduce, isolate, and submit a PR upstream.

**Date observed:** 2026-05-25 during Phase 12a (Related Tasks wire) of tesserabx-pm.

**Hit on:** Mike's laptop running the host TesseraBX dev stack in Docker, app container based on the host's standard image.

## Environment

| Component | Version |
| --- | --- |
| BoxLang | v1.13.0+54 |
| CBWire | 4.x (whatever ships with the host's box.json at the time of writing) |
| TestBox | v7.0.0 |
| ColdBox | 8 |
| OS in container | Debian (root user, `/app` workdir) |
| Source location | `modules/tesserabx-pm/wires/` (bind-mounted from host) |

## TL;DR

Under a not-yet-isolated combination of HTML nesting depth, line count, and `<bx:if>` / `<bx:loop>` placement, CBWire's `RendererEncapsulator.cfm` writes a **truncated** copy of a wire's `.bxm` template to its tmp cache directory. The trailing closing tags get silently dropped, BoxLang then errors on the next include with:

```text
Error compiling [ /app/modules/cbwire/views/tmp/{HASH}.bxm ]
Line: 1 Col: 0 - Unclosed output tag on line 1
<bx:output>
^^^^^^^^^^
```

The error is misleading: line 1 is fine. The actual problem is that the *last* lines of the file (the matching `</bx:output>` and surrounding closing tags) were never written.

## Symptom in numbers

The exact template that triggered the bug:

* Source file: `modules/tesserabx-pm/wires/relatedTasks.bxm`
* Source: **31 lines, 1391 bytes**, MD5 `b20e3c145107b618cdc304bbb7ec885c`
* Both host and container saw identical bytes (verified `wc -c`, `md5sum`, `od -c`)

After a normal page render that embedded this wire:

* tmp file: `/app/modules/cbwire/views/tmp/E9102FB58F82D9F609AA0079F5DCB73B.bxm`
* Size: **24 lines, 1275 bytes** (116 bytes / 7 lines short)
* The lost content: the trailing `</li>`, `</bx:loop>`, `</ul>`, three `</div>` closes, and `</bx:output>` — i.e., the entire closing block of nested tags after the inner `<div class="small text-body-secondary">` close

The hash filename `E9102FB58F82D9F609AA0079F5DCB73B` is generated by `hash( normalizedPath )` inside `RendererEncapsulator.cfm` at line 130.

## Bad source template (reproduction candidate)

This is the template that consistently produced a truncated tmp file. Copy verbatim into `wires/SomeWire.bxm` (paired with a normal `SomeWire.bx` class) when trying to reproduce:

```bxm
<bx:output>
<bx:script>
    local.matches    = rows();
    local.hasMatches = arrayLen( local.matches ) > 0;
    local.wrapStyle  = local.hasMatches ? "" : "display:none";
</bx:script>

<div data-pm-wire-id="#_getID()#" style="#local.wrapStyle#">
    <div class="card">
        <div class="card-body">
            <h2 class="h6 mb-2 text-body-secondary"><i class="bi bi-stars"></i> Related tasks</h2>
            <ul class="list-unstyled mb-0">
                <bx:loop array="#local.matches#" item="m">
                    <li class="border-top pt-2 pb-2">
                        <a href="/agent/pm/tasks/#encodeForURL( m.id )#" class="text-decoration-none">
                            <strong class="small">#encodeForHTML( m.title )#</strong>
                        </a>
                        <div class="small text-body-secondary">
                            <span class="badge text-bg-light border me-1">#scorePercent( m.distance )#% similar</span>
                            <bx:if len( m.priority )>
                                <span class="badge text-bg-light border me-1">#encodeForHTML( m.priority )#</span>
                            </bx:if>
                            <span>in #encodeForHTML( m.project_name )#</span>
                        </div>
                    </li>
                </bx:loop>
            </ul>
        </div>
    </div>
</div>
</bx:output>
```

Pair this with the working class `wires/RelatedTasks.bx` from the same phase (extends `cbwire.models.Component`, has a `rows()` method returning an array of structs with at least `id`, `title`, `distance`, `priority`, `project_name`, plus a `scorePercent( distance )` method).

The truncation reproduced **every single render**, not intermittently.

## Workaround that fixed it (current state in the repo)

Flatten the template aggressively: fewer indentation levels, fewer lines, conditionals collapsed onto a single line, no top-of-file `<bx:script>` precomputation block. The currently-shipping version in `wires/relatedTasks.bxm` is 17 lines, 877 bytes, and renders correctly.

That outcome means **either** the bug correlates with line count / byte count above some threshold, **or** with a particular nesting / conditional pattern that the flattened version no longer exercises. We did not narrow it further before unblocking the phase.

## Things we ruled out

1. **Source file corruption.** `md5sum` matched between host and container; `wc -c` matched; `od -c` showed clean 7-bit ASCII with Unix `\n` line endings, no BOM, no null bytes, no stray `\r`, no UTF-8 multi-byte sequences.

2. **Wrong code path.** The truncated file is at `cbwire/views/tmp/{hash}.bxm`, written by `RendererEncapsulator.cfm`. CBWire also has a `SingleFileComponentBuilder` that writes to `cbwire/models/tmp/{name}.bxm`, but that path is for single-file components (where the wire's class and template live in one `.bxm` with `@startWire` / `@endWire` annotations inside a `<bx:script>` block). Our wire uses the conventional two-file pattern (`RelatedTasks.bx` class + `relatedTasks.bxm` template).

3. **Preprocessor matches.** CBWire's `CBWIREController.getPreprocessors()` registers three preprocessors, in order:

   * `TemplatePreprocessor` — replaces `<cbwire:script>`, `</cbwire:script>`, `<cbwire:assets>`, `</cbwire:assets>` with `<cfsavecontent>` / `</cfsavecontent>` wrappers
   * `CBWIREPreprocessor` — matches the regex `<cbwire:(\w+)\s*(.*?)\/?>` and replaces each match with a `#wire( name=..., params=..., lazy=false )#` call
   * `TeleportPreprocessor` — replaces `@teleport( selector )` with `<template x-teleport="selector">` and `@endteleport` with `</template>`

   None of those triggers appear in our template (`grep -E "<cbwire:|@teleport|@endteleport"` returned no matches), so each preprocessor's `handle()` should pass content through unchanged.

4. **Bind mount staleness.** The host and container both reported the same source bytes and the same `stat` size at the same instant. The container's clock matches the host's.

5. **Concurrent writes.** The wire is embedded exactly once on the task show page. No other request would be racing to compile the same hash file. (We did not, however, prove this by adding instrumentation — see the "What to instrument" section below.)

## Where the bytes are dropped

`cbwire/views/RendererEncapsulator.cfm` lines 11-15:

```cfml
function preprocessAndCacheFile(sourcePath, cachePath) {
    var content          = fileRead( expandPath( sourcePath ) );
    var processedContent = preprocessFile( content );
    fileWrite( cachePath, processedContent );
}
```

One of those three steps lost 116 bytes between source on disk (1391 bytes) and tmp on disk (1275 bytes). We don't know which. The hypothesis ranking:

1. **`fileWrite` truncating during write.** Most likely. BoxLang's `fileWrite` ultimately drives a Java `FileWriter` / `Files.write`; a partial write would explain the exactly-at-line-boundary cutoff. If the writer is closed before the buffer is flushed under specific content shapes, we'd see exactly this symptom. Worth verifying by stepping into BoxLang's `FileWrite` implementation with the bad-template content and observing whether `processedContent` has the expected length before the write call.

2. **`preprocessFile` returning truncated content.** Less likely because none of the three preprocessor regexes should match anything in our template. Could still happen if one of them has an undocumented side effect or a string-builder buffer length cap.

3. **`fileRead` returning truncated content.** Least likely; `fileRead` is well-trodden, and the same file reads correctly when we `cat` it from inside the container.

## What to instrument when reproducing

Add temporary `writeLog` calls to a copy of `RendererEncapsulator.cfm` (or wrap `preprocessAndCacheFile`):

```cfml
function preprocessAndCacheFile(sourcePath, cachePath) {
    var content = fileRead( expandPath( sourcePath ) );
    writeLog( text = "tmp-trunc read=" & len( content ) & " src=" & arguments.sourcePath, log = "cbwire" );

    var processedContent = preprocessFile( content );
    writeLog( text = "tmp-trunc processed=" & len( processedContent ), log = "cbwire" );

    fileWrite( cachePath, processedContent );

    var writtenSize = getFileInfo( cachePath ).size;
    writeLog( text = "tmp-trunc written=" & writtenSize, log = "cbwire" );
}
```

Then:

* If `read` < source size, the bug is in `fileRead`.
* If `processed` < `read`, the bug is in one of the preprocessors.
* If `written` < `processed`, the bug is in `fileWrite` (or its underlying Java path).

The third outcome is the most likely; if confirmed, the next step is to reproduce inside a pure BoxLang script:

```cfml
var s = fileRead( "/app/modules/tesserabx-pm/wires/relatedTasks.bxm" );
echo( "len=" & len( s ) & chr( 10 ) );
fileWrite( "/tmp/probe.txt", s );
echo( "wrote=" & getFileInfo( "/tmp/probe.txt" ).size & chr( 10 ) );
```

If that reproduces with `wrote < len`, the bug is in BoxLang core and the upstream PR target is the BoxLang repo, not CBWire. If `wrote == len`, the bug is in CBWire's call site.

## 2026-05-25 update: confirmed cause for at least one variant

Mike isolated a likely cause while building the Phase 13a collapsible Activity card in `wires/projectEventFeed.bxm`. The template included a Bootstrap collapse toggle whose `data-bs-target` attribute needed a CSS selector starting with `#`:

```bxm
<!-- BROKE the parser; produced "Unclosed output tag on line 1" -->
<button data-bs-target="##encodeForHTMLAttribute( local.bodyId )#" ...>
```

Replacing the `##` literal-hash escape with the BoxLang BIF `#char(35)#` (which evaluates to ASCII 35 = `#`) parsed cleanly:

```bxm
<!-- WORKS -->
<button data-bs-target="#char(35)##encodeForHTMLAttribute( local.bodyId )#" ...>
```

Hypothesis: BoxLang's `<bx:output>` parser cannot reliably decide whether `##expression(...)#` means "escaped literal `#` followed by a new `#expression#`" or some single tangled expression. The failure surfaces sometimes as the truncated tmp file documented above, and sometimes as the "Unclosed output tag on line 1" parse error pointing at the file's opening `<bx:output>`. `#char(35)#` is one unambiguous expression with no escape semantics involved, so the parser does not get confused.

This may not be the same bug as the Phase 12a Related Tasks truncation (which had no `##`-adjacent-expression pattern in the source), but it produces the same misleading error and falls under the same "wire tmp file is shorter than the source" symptom class. Both fix paths (flatten the template, swap `##` for `#char(35)#`) are zero-cost workarounds while the underlying parser is investigated.

## Patterns that may correlate (untested hypotheses)

Things worth varying in a binary-search reproduction:

* **Top-of-file `<bx:script>` block** that sets locals (`local.matches`, `local.hasMatches`, `local.wrapStyle`). The flattened workaround eliminated this block in favor of inline `<bx:set>` and an inline `<bx:if>` in the attribute.
* **Inline conditional inside an HTML attribute**, e.g. `style="#local.wrapStyle#"`. We tried both attaching the conditional via a precomputed `local.wrapStyle` (broken) and inlining `<bx:if !arrayLen( local.matches )> style="display:none"</bx:if>` (we never got far enough to confirm whether THIS specifically broke — the earlier breakage was upstream).
* **`<bx:loop>` containing a `<bx:if>` containing nested HTML.** Common pattern, so if this is the trigger, lots of existing wires should be at risk; that they aren't suggests the trigger is something tighter.
* **Indentation depth.** The broken template indents up to 32 spaces; the working version dedents.
* **Multiple sibling `<span>` elements inside a single `<div>`.** The cut occurred right before the second sibling `<span>` (the "in {project}" one) — but that's also the bx:loop's interior. Unclear which dimension matters.

## Workaround until fix lands

Keep CBWire `.bxm` templates as flat as possible:

* Avoid more than 4-5 levels of HTML nesting.
* Avoid wrapping the entire wire body in a single `<bx:if>` (CBWire's separate "wire must have at least one root element" rule makes this fragile anyway — always render an outer `<div data-pm-wire-id>` and gate visibility via inline CSS).
* Avoid top-of-file `<bx:script>` blocks that precompute display state when an inline `<bx:set>` or an inline conditional in the attribute works.
* Inline trivial conditionals (`<bx:if>` inside attributes / inside single-element bodies) where possible.

A reasonable rule of thumb: if a wire's template body exceeds ~30 lines or ~1.3 KB and uses `<bx:loop>` over a non-trivial nested HTML body, hand-test the tmp file size after first render to confirm CBWire wrote the full content.

## Open questions for the upstream PR

1. Is the truncation `fileWrite`-side or `preprocess`-side? (Logging recipe above pins it down.)
2. If `fileWrite`: is it specific to a content shape, or to write-then-immediately-read in the same request?
3. Does CBWire need an explicit `fileWrite( ..., charset = "UTF-8" )` or an explicit flush?
4. Should `RendererEncapsulator.preprocessAndCacheFile` verify post-write size against `len( processedContent )` and re-write or fail loud if they differ? That would at least make the bug noisy instead of producing a parse error two layers downstream.
